# K230 视觉处理架构踩坑记录：为什么 01 行而 02 不行？

在实现“彩色 IDE 预览 + 黑白二值化识别”的复合需求时，我们尝试了两种完全不同的架构路径。最终 `rect_01.py` 成功稳定运行，而 `rect_02.py` 遭遇了底层硬件崩溃。

以下是深度的技术复盘，这对后续 K230 乃至其他带有硬件加速器 (ISP/KPU) 的 AI 芯片开发具有重要的参考价值。

## 一、 方案回顾

### 方案 A：`rect_01.py` (成功方案 - 软件流)
*   **硬件采集**：通道 0 (`chn0`)，格式为 **RGB565** 彩色。
*   **软件处理**：每一帧通过 `img.copy().to_grayscale().binary()` 在内存中动态生成一张二值化黑白副本，在此副本上运行算法。
*   **输出**：在原始彩色 `img` 上画框，并输出到 IDE。

### 方案 B：`rect_02.py` (失败方案 - 硬件分离流)
*   **硬件采集**：试图将 `chn0` 设置为主流的 `YUV420SP`，同时开启次流 `chn2` 为 `RGB565`（或尝试直接配置多通道）。
*   **尝试路径**：企图通过底层的不同 Channel 直接拿数据，绕过软件复制。
*   **报错现象**：
    *   `buffer_size 0`
    *   `sensor(0) snapshot chn(0) failed(3)` (或者 chn2 failed)

---

## 二、 失败根因深度剖析

`rect_02.py` 失败的核心原因在于 **K230 严格且缺乏弹性的底层硬件资源池 (VB Pool) 分配机制**。

### 1. 视频内存池 (Video Buffer Pool) 的分配冲突
在 01Studio 提供的 CanMV 固件（V1.4+）中，`Sensor()` 的初始化是一个极其敏感的步骤。
*   当系统尝试为摄像头分配内存时，它必须预先知道图像的宽高。
*   如果你在底层同时激活多个不同格式、不同用途的 Channel（比如既要 IDE 的 VIRT 虚拟显示，又要 YUV 的主流，又要 RGB 的次流），K230 的多媒体管理器 (`MediaManager`) 极大概率无法在仅有的少数几个 Pool（日志显示只有 4 个 pool）中找到合适的内存块分配方案。
*   **结果**：内存分配器返回 0 大小的 Buffer（`buffer_size 0`），导致后续的 `snapshot` 直接发生硬件死锁（超时 `failed(3)`）。

### 2. ISP (图像信号处理器) 的管道约束
K230 的硬件 ISP 在处理数据流时有固定的 Pipeline 规则。
*   在官方的 `camera_single_show_lcd` 例程中，虽然展示了 `chn0` 跑 YUV，`chn2` 跑 RGB 的多通道能力，但这通常需要配合真实的物理屏幕（如 HDMI 或 LCD 驱动）来消费这些数据流。
*   而在我们的应用场景中，由于我们使用的是虚拟的 IDE 屏幕 (`Display.VIRT`)，硬件显示控制器的中断时序可能与多通道的 `snapshot` 抓取时序产生了冲突。

### 3. `binary()` 算子与图像对象的耦合
在 `02` 版的某些尝试中，我们甚至试图让硬件直接吐出灰度图，然后直接 `to_ide=True`。但由于我们要彩色预览，被迫切回 RGB565。
*   当我们在硬件直接输出的单一图像流上做复杂的格式强转时，很容易破坏 `MediaManager` 维护的图像结构体。

---

## 三、 为什么 01 方案能行？

`rect_01.py` 成功避开了所有的底层“雷区”，采用了**“硬件最简，软件代劳”**的策略：

1.  **极简的硬件流水线**：底层的 `Sensor` 和 `MediaManager` 只需维护唯一的一条、最标准的流水线 —— `320x240 RGB565` 输出到 `Display.VIRT`。这保证了硬件层绝对不会崩溃。
2.  **安全的内存隔离**：`img.copy()` 是真正的灵魂。它在 MicroPython 的堆内存 (Heap) 中开辟了一块与底层硬件 VB Pool 完全无关的隔离区。
3.  **无损算法计算**：我们在软件 Heap 中的副本上进行灰度转换 (`to_grayscale`) 和二值化 (`binary`)，这些纯软件操作虽然消耗了一些 CPU 周期（导致帧率掉到 30fps），但绝对不会触发硬件级的锁死或越界。

## 四、 结论与最佳实践

对于 K230 (CanMV) 这类系统：
**当遇到复杂的“一边显示 X，一边处理 Y”的需求时，除非官方例程有完全一致的现成模板，否则永远优先采用“单通道硬件抓图 + 软件 `copy()` 后处理”的架构。**

牺牲 10~20 的 FPS（从 60 掉到 30）换取整个系统 100% 的底层稳定性，在电赛这类对可靠性要求极高的场景中，是绝对划算且必要的妥协。
